# M0 签名材料扫描

日期：2026-09-18；2026-09-19 两次扩展（嵌套归档 → 全部模块 assets 根 + APK 产物侧）

## 扫描范围

- 扩展名集合：`.jks`、`.keystore`、`.p12`、`.pkcs12`、`.pem`、`.key`
- 源根（2026-09-19 起由 `rootProject.subprojects` 枚举，不再手写清单）：
  - `:app/src/main/assets`
  - `:app/build/generated/main-assets`（`syncMainAssets` 的合并输出，与上一项内容重叠）
  - 各库模块 `src/main/assets`，实际存在的是 `:terminal/src/main/assets`
- 容器成员名：`.apk`、`.zip`、`.jar`、`.aar` 展开一层后按同一扩展名集合匹配
- 人工补充核查：PKCS#8 `BEGIN PRIVATE KEY` 文本标记、APK v1 签名文件（`META-INF/*.RSA|DSA|EC|SF|MF`）

改动动因：`:terminal/src/main/assets` 里的 64 MB Ubuntu rootfs 会经 `merge<Variant>Assets` 进入 APK，但旧扫描根只有 `:app`，属实体盲区。

## 结果

### 容器成员（逐个流式核查，成员数 / sha256 前缀）

| 容器 | 成员 | 结论 |
|---|---|---|
| `accessibility.apk` | 912 / `b6bac271` | 无匹配扩展名、无私钥标记、无 v1 签名文件 |
| `desktop.apk` | 161 / `76f6eb10` | 同上 |
| `shizuku.apk` | 934 / `6e273ab0` | 同上 |
| `subpack/android.apk` | 431 | 同上；Flutter 产物，含 arm64-v8a/armeabi-v7a/x86_64 的 `libapp.so`/`libflutter.so` |
| `subpack/windows.zip` | 30 | 同上；含 `assistance_subpack.exe`、`flutter_windows.dll`、WebView2 DLL |
| `:terminal/…/ubuntu-noble-aarch64-pd-v4.18.0.tar.xz` | 12,684 | **146 个 `.pem`，全部位于 `etc/ssl/certs/`（公共根证书及其软链）**；`etc/ssl/private/` 为空目录；`.key`/`.p12`/`.pkcs12`/`.jks`/`.keystore`/`ssh_host*`/`id_rsa` 命中 0。判定：不含私钥材料 |

rootfs 用 `tar tvfJ` 流式核查，因此**没有**把它纳入门禁的自动展开集合：`.tar.xz` 需要 XZ 解码，且按当前"只匹配扩展名"的规则一旦纳入就会把 146 个公共 CA 证书判成误报。要让门禁覆盖 tar/xz，前置条件是区分公钥证书与私钥（解析 PKCS#8，或结合路径与 `PRIVATE KEY` 标记），不是再加一个扩展名。

`operit_shell_exec`、`templates/**/aapt2-arm64-v8a` 为非归档 ELF，按扩展名规则不适用，来源与许可另记在 `license-inventory.md`。

对 `app/build/outputs/apk/clone/app-clone.apk`（413,136,822 B，5,550 条目）：ZIP 成员中无上述扩展名，无 v1 签名文件（v1 未启用，见 `build-manifest.json` 的 `signing.schemeObserved`），`lib/` 下只有 `arm64-v8a`。产物内的 assets 与上表源侧一致。

## 已知限制

- 匹配依据仍是**文件名后缀**，不解析内容结构：改名成 `.bin` 的密钥库、或 v2/v3 签名块内容都不会命中。这是降低遗漏，不是证明不存在。
- 只展开一层归档；归档内的归档（如 APK 内的 zip）不递归。
- `.tar`/`.tar.xz` 不自动展开（理由见上），依赖一次性人工核查。
- flavor / 非标准 `assets.srcDirs` 不覆盖：枚举的是各模块的 `src/main/assets` 约定路径。当前仓库无此用法，新增时需要一并扩展。
